# User preview and legacy nil-flag semantics

The owner shared Phase 3 preview screenshots from the original 3.3.5a client,
build 12340, Interface 30300. Eight occupied bag slots appeared as
`UNKNOWN ... reason=LOCK_UNKNOWN`; empty slots appeared as `KEEP ...
reason=EMPTY_SLOT`. This confirms the preview module runs and the bag contents
are observed, while the adapter's earlier nil-lock interpretation prevented
classification.

The interpretation was checked against the pinned stock 3.3.5 FrameXML source
at commit `d0339b17b0221db76e6acd2dc2915d224a5b62ca`:

- `ContainerFrame.lua:747` enables stack splitting when `not locked`, so a
  successful nil third return is the ordinary unlocked state.
- `ContainerFrame.lua:292` hides the quest marker when neither `questId` nor
  `isQuestItem` is truthy; the observed three-nil tuple therefore means no quest
  marker.
- `ContainerFrame.lua:632-633` suppresses the refund prompt when `refundSec` is
  absent; a successful zero-return purchase-info call follows this no-refund
  path.

The legacy adapter now maps those successful falsey results to false. A missing
or throwing API read still produces `unknown`. This is a compatibility
interpretation based on stock FrameXML and the owner's matching tuple shapes;
it does not establish how every modified private-server client behaves.

No inventory operation was attempted. The rule preview remains read-only.
